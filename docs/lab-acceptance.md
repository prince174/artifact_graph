# Приёмочная матрица на текущем Cloud/TeamCity-стенде

Это воспроизводимая проверка интеграции на настоящих BB-репозиториях и TC-билдах.
Она расширяет исходный стенд, а не заменяет его. Манифест данных и ожидаемых результатов:
[`app/lab_matrix.py`](../app/lab_matrix.py), ключ владения `artifact-graph-lab-v1`.

Ниже описаны процедура и критерии успеха; зафиксированный результат проведённого прогона
приведён в конце документа. Для каждого нового запуска подтверждение — свежий JSON-отчёт
валидатора и результат браузерных тестов, а не только выполнение команд подготовки.
Успех на Bitbucket Cloud не подтверждает доступность, права или совместимость вашего
Bitbucket Data Center в production. Для DC остаётся отдельный пилот из
[README](../README.md#bitbucket-data-center-production).

## Что создаётся

| Объект | Добавляется | Назначение |
|---|---:|---|
| BB-проекты | 10: `LAB01`…`LAB10` | Пересечь лимит первых 10 проектов |
| BB-репозитории | 11 | По одному в новых проектах и `lab-overflow` в существующем `DEMO` |
| TC-проекты | 7 | Родитель `LabMatrix` и 6 продуктовых подпроектов |
| TC-билдконфигурации | 16 | Реальные команды, цепочки стадий, отрицательные сценарии |

При исходных 1 BB-проекте, 10 репозиториях и 30 TC-конфигурациях итог — 11 BB-проектов,
21 репозиторий и 46 TC-конфигураций. Существующие репозитории/конфигурации не перезаписываются.
У `DEMO` добавляется только новый репозиторий; настройки самого проекта не меняются.
На графе нет workspace, `_Root`, отдельного образа или SBOM: только
`BB project → repository → TC project → build configuration → build`.
Родитель `LabMatrix` не имеет собственных билдконфигураций; рабочие связи идут через его
шесть продуктовых подпроектов.

| Репозиторий / TC-подпроект | Проверяемый результат |
|---|---|
| `lab-maven` / `Maven` | Ветка `release/lab`, настоящий Maven/Java; `docker push` вызывается из `pom.xml`; `target/sbom.json`; Test → Build → Deploy |
| `lab-python` / `Python` | Python-тест, два реальных push одного образа с тегами `:1` и `:2` из `ci/publish.sh`; SBOM нет |
| `lab-npm` / `Npm` | npm/Node-тест и сборка; два разных `**/sbom.json`, обычный `result.txt` не считается SBOM |
| `lab-podman` / `Podman` | Настоящий `podman build` и `podman push`, не оболочка вокруг Docker |
| `lab-maven`, `lab-empty` / `Shared` | Раздельные Alpha/Beta в одном TC-проекте; Composite использует два VCS root с разными checkout paths |
| `lab-negative` / `Negative` | Echo с текстом `docker push` не подтверждает push; FailedPush намеренно падает; InvalidSbom публикует файл с ошибкой JSON |
| `lab-empty`, `lab-canary-07`…`10`, `lab-overflow` | Репозитории без найденных целевых результатов; canary/overflow не имеют TC-сборок |

`lab-empty` содержит README: это репозиторий без артефактных команд, не пустой Git без коммитов.
В `lab-negative` наличие `sbom.json` и его валидность различаются: файл найден, но
`sbomStatus=invalid_json`. Красные билды `Negative_FailedPush` ожидаемы и не означают отказ сервиса.
Тестовые Deploy-стадии не выполняют развёртывание в production.

## 1. Подготовка и границы доступа

Все команды выполняются из корня репозитория. Для host-скриптов нужны Python 3.12+, Git
и зависимости проекта; сам сервис продолжает работать в контейнере:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[test,e2e]'
```

В PowerShell вместо `source` используйте `.\.venv\Scripts\Activate.ps1`.
Не заменяйте уже заполненный `.env` копией примера. Проверьте/добавьте значения локально:

```env
APP_MODE=live
BITBUCKET_PROVIDER=cloud
BITBUCKET_WORKSPACE=artifact_graph
TEAMCITY_BOOTSTRAP_URL=http://localhost:18111
TEAMCITY_READER_USERNAME=user
TEAMCITY_BUILD_LIMIT=5
GRAPH_PORT=18082
GRAPH_URL=http://localhost:18082
```

Это адреса текущего стенда, а не обязательные порты продукта. Для запуска скриптов внутри
его Docker-сети используйте `TEAMCITY_BOOTSTRAP_URL=http://teamcity:8111` и
`GRAPH_URL=http://graph:8080`; host-адрес `localhost` внутри контейнера указывает на него самого.
`TEAMCITY_URL` в окружении runtime остаётся внутренним адресом TC.
Переменные процесса имеют приоритет над `.env`: не оставляйте тестовый `WEB_PASSWORD`
в shell/container, из которого запускается live-проверка.

Секреты хранятся только в игнорируемом `.env` или защищённом окружении:

- `BB_BOOTSTRAP_EMAIL`, `BB_BOOTSTRAP_TOKEN` — временные права создания проектов/репозиториев
  и записи тестовых исходников только в тестовом workspace.
- `TC_ADMIN_TOKEN` — отдельный токен администратора текущего TC-стенда для provisioning/queue.
- `BITBUCKET_TOKEN` — RO-токен сборщика; `BITBUCKET_EMAIL` — email его учётной записи при API token.
  Доступ должен включать нужные workspace, проекты, репозитории и исходники.
- `TEAMCITY_TOKEN` — токен отдельного пользователя с `Project Viewer`, без прав запуска и изменения.
  `TEAMCITY_READER_USERNAME` должен указывать на уже существующего этого пользователя.
- `BB_CHECKOUT_TOKEN` — отдельный RO-токен для Git checkout. Можно явно выбрать вместо него
  проверенный Git-чтением `BITBUCKET_TOKEN`, как в командах ниже. Подмена bootstrap-токеном запрещена.
- `WEB_USERNAME`, `WEB_PASSWORD` — учётная запись входа в граф, не токены BB/TC.

Токены администратора не передаются graph-контейнеру. Приложение читает BB/TC только через GET;
записывающие bootstrap-скрипты — отдельный инструмент. Само имя переменной не ограничивает
права токена: проверьте их в BB/TC, включая унаследованные группы TeamCity.

## 2. Агент с Maven и нативным Podman

```bash
docker compose -f compose.yaml -f compose.lab.yaml --profile build-lab up -d --build teamcity-agent
docker compose up -d --build --no-deps graph
```

[`compose.lab.yaml`](../compose.lab.yaml) добавляет агенту Maven, Node/npm, Python и Podman;
Podman использует `vfs`. Базовый lab-профиль привилегированный, необходим только для исполнения
доверенных тестовых сборок. Не объединяйте его с `compose.prod.yaml` и не используйте такой
агент для недоверенных репозиториев. В production графу build-agent вообще не нужен.

В TeamCity проверьте имя/адрес именно нового lab-агента, авторизуйте его и дождитесь подключения.
Provisioning не авторизует автоматически всех агентов. TC должен иметь свободную ёмкость
для 16 дополнительных конфигураций. Для state-check ниже нужен ровно один подключённый,
авторизованный и включённый агент. Не удаляйте volumes TC/registry при повторном запуске.

## 3. Предварительная проверка и создание

```bash
python scripts/bootstrap/expand_lab.py --env-file .env --checkout-token-env BITBUCKET_TOKEN --plan
python scripts/bootstrap/expand_lab.py --env-file .env --checkout-token-env BITBUCKET_TOKEN --apply
```

Без `--apply` выполняются только чтение API и Git `ls-remote`: проверяются workspace, доступ,
ёмкость TC, владение существующими объектами и соответствие исходников/конфигураций манифесту.
По умолчанию Git-доступ проверяется на исходном `java-maven-api`; другой уже существующий
доступный репозиторий задаётся через `--checkout-probe-repo`.

`--apply` создаёт недостающие управляемые объекты, заполняет исходники, назначает ветки и VCS roots,
настраивает шаги, правила артефактов и snapshot dependencies. В конце пользователю
`TEAMCITY_READER_USERNAME`, если он указан, добавляется `Project Viewer` на `LabMatrix`.
Исходный доступ к `Demo` сохраняется. Provisioning не запускает сборки.

Метки владения содержат ключ матрицы и SHA-256 описания объекта. При совпадении чужого имени,
изменённом содержимом или несовпадении плана инструмент останавливается, а не перезаписывает объект.
Повторный запуск разрешён для той же матрицы. Если предыдущий запрос завершился неоднозначно,
сначала снова выполните `--plan` и проверьте TC/BB. Не удаляйте вручную чужие объекты и не
подделывайте метку, чтобы обойти проверку. Старый `bootstrap_cloud.py` для такого расширения не нужен.

### Ротация RO-токена Git checkout

Замена `BB_CHECKOUT_TOKEN` или выбранного через `--checkout-token-env` значения `BITBUCKET_TOKEN`
в `.env` **не обновляет пароль уже существующих VCS roots в TeamCity**. Повторный
`expand_lab.py --apply` сохраняет их секреты; новый токен используется при создании новых roots
и для отдельной проверки Git-доступа. Успешный `--plan` поэтому не доказывает, что TC checkout
уже переключился на новый токен.

Поле отчёта `existingCheckoutTokensUnchanged` перечисляет существующие VCS root ID, секреты
которых инструмент оставил без изменений. Это предупреждение, а не результат проверки равенства
секретов: скрытое значение пароля TC не используется для такого сравнения.
Автоматического скрипта ротации сохранённых checkout credentials здесь нет.

Безопасная ручная процедура:

1. Создайте новый RO-токен с доступом к тем же тестовым репозиториям. Старый пока не отзывайте.
   Сохраните новый токен только в выбранной переменной локального `.env` и выполните
   `expand_lab.py --plan` с тем же явным `--checkout-token-env`.
2. В настройках TC-проекта `LabMatrix` найдите именно управляемые VCS roots из списка ниже.
   Сверьте ID, проект-владелец `LabMatrix`, маркер `artifact-graph-lab-v1`, URL нужного workspace
   и ветку. Не применяйте массовую замену ко всем VCS roots сервера или по одному совпадению префикса.
3. После завершения использующих их билдов в каждом проверенном root замените только пароль
   Git-аутентификации новым RO-токеном. Не меняйте URL, ветку, username
   `x-bitbucket-api-token-auth`, метки владения и roots исходного `Demo`.
4. Проверьте соединение каждого root средствами TeamCity и выполните тестовые сборки с реальным
   получением исходников. В частности, проверьте Composite: он использует одновременно Maven
   и Empty roots. Проверьте журнал checkout, а не только факт повторного использования уже
   готового workspace на агенте.
5. Если ротируется также runtime `BITBUCKET_TOKEN`, пересоздайте только `graph` командой
   `docker compose up -d --no-deps --force-recreate graph` и дождитесь успешного скана.
   Убедитесь, что checkout в TC и чтение сборщиком работают на новых credentials; только после
   этого отзывайте старый токен. Если тот же старый токен использует другой контур, сначала
   отдельно переключите и проверьте его — не меняйте чужие roots в рамках этой процедуры.

| VCS root ID | Репозиторий | Ветка |
|---|---|---|
| `LabMatrix_Vcs_lab_maven` | `lab-maven` | `release/lab` |
| `LabMatrix_Vcs_lab_python` | `lab-python` | `main` |
| `LabMatrix_Vcs_lab_npm` | `lab-npm` | `main` |
| `LabMatrix_Vcs_lab_podman` | `lab-podman` | `main` |
| `LabMatrix_Vcs_lab_negative` | `lab-negative` | `main` |
| `LabMatrix_Vcs_lab_empty` | `lab-empty` | `main` |

Не выводите пароль через API, `docker compose config`, логи, shell history или скриншоты.
При неудаче остановитесь до отзыва старого токена; возвращайте сохранённый прежний пароль только
в проверенные roots этой матрицы и выясняйте причину, не расширяя права нового RO-токена до write/admin.

## 4. Реальные сборки и окно последних пяти

```bash
python scripts/bootstrap/run_lab.py --env-file .env --plan
python scripts/bootstrap/run_lab.py --env-file .env --apply --timeout 1800 --interval 5
```

Runner проверяет точные настройки и владение конфигурациями, включая их snapshot dependencies,
и запускает только конфигурации манифеста. Он не меняет настройки, не включает paused-конфигурации
и не отменяет существующие билды. При уже активном билде конфигурации второй запрос не отправляется.

Цель — не менее 3 завершённых запусков каждой конфигурации и не менее 5 у `Maven_Build`.
Все элементы её текущего окна последних пяти должны иметь ожидаемый SUCCESS/FAILURE, поэтому
после неудачного промежуточного запуска могут потребоваться дополнительные сборки.
Snapshot dependencies тоже могут запускать стадии: точное общее число запусков не фиксировано.
Ограничения времени и `--max-new-builds` останавливают пополнение при постоянной ошибке;
оставшиеся в TC сборки намеренно не отменяются.

Для адресной проверки поддерживается повторяемый `--config`, например:

```bash
python scripts/bootstrap/run_lab.py --env-file .env --config LabMatrix_Podman_Build --apply --max-new-builds 10
```

Если цель не достигается, изучите лог именно соответствующего fixture-билда: Git/сеть,
доступ к Maven-репозиториям, Docker daemon, `registry:5000`, запуск Podman.
Не выдавайте RO-токену права записи для исправления ошибки checkout.

## 5. Автоматическая сверка графа с TeamCity

После опустошения очереди и завершения билдов:

```bash
python scripts/validate_lab.py --env-file .env --url http://localhost:18082 --tc-url http://localhost:18111 --build-limit 5 --min-builds 3 --refresh --timeout 900
```

Валидатор использует только `TEAMCITY_TOKEN`, не admin-token. Без `--refresh` он лишь читает;
`--refresh` дополнительно запрашивает CSRF-защищённое обновление самого графа и ждёт успешного скана.
`--tc-url` имеет приоритет над `TEAMCITY_BOOTSTRAP_URL`, затем `TEAMCITY_URL`.
Для CA можно передать `--ca-file /path/to/ca.pem`, не отключая TLS verification.
`--output lab-report.json` создаёт новый локальный JSON, но не перезаписывает существующий файл.
Не коммитьте отчёты, содержащие имена/адреса из закрытого окружения, без проверки их содержимого.

Успех — exit code 0 и `status: success`. Проверяются:

- свежий успешный live-скан без stale/incomplete-узлов;
- поиск каждого из 11 новых репозиториев с точным набором связанных TC-конфигураций;
- отдельная сверка текущих ID, статусов и количества билдов через TC API;
- точные push-теги с подтверждением в build log, пути источников `pom.xml`/скрипта;
- пути SBOM, включая оба файла npm и ошибочный JSON отрицательного сценария;
- флаги/цвета билдов, отсутствие ложной подсветки `lab-empty` через соседнюю Alpha-конфигурацию;
- только пять пользовательских типов узлов, корректные связи, отсутствие дубликатов,
  висящих рёбер и узлов без позиции;
- все страницы графа, отсутствие повторяющихся страниц и лимиты 10 проектов / 10 репозиториев.

По сортировке этого стенда первый экран содержит `DEMO` и `LAB01`…`LAB09`, следующая страница —
`LAB10`. Добавленный `lab-overflow` попадает в середину сортировки `DEMO`, поэтому за лимит первых
10 выходит исходный `terraform-infra`, а не сам `lab-overflow`. Оба скрытых случая остаются
доступны поиском; проверка `terraform-infra` дополнительно входит в live-браузерный сценарий.

## 6. Running, queued, paused и восстановление

Эта проверка временно меняет только собственные тестовые конфигурации. Сначала дождитесь отсутствия
любых выполняющихся/ожидающих билдов в TC, ровно одного готового агента и хотя бы одного
завершённого отрицательного `LabMatrix_Negative_FailedPush`:

```bash
python scripts/bootstrap/check_lab_states.py --env-file .env --plan
python scripts/bootstrap/check_lab_states.py --env-file .env --apply --timeout 180
```

`--apply` временно приостанавливает `LabMatrix_Shared_Beta`, заменяет шаг собственного
`LabMatrix_Shared_Composite` ожиданием и создаёт два запуска, чтобы одновременно увидеть running
и queued. После обновления графа проверяются running/queued/paused/failed-состояния.
В `finally` инструмент независимо пытается отменить только созданные этим запуском билды,
восстановить исходные шаги Composite, paused-состояние Beta и обновить граф.
Ошибки очистки не скрываются: вывод содержит соответствующие действия и созданные ID.

История отменённых сборок сохраняется в TeamCity. Перед финальной приёмкой заполните окно
Composite успешными запусками и снова проверьте граф:

```bash
python scripts/bootstrap/run_lab.py --env-file .env --config LabMatrix_Shared_Composite --apply
python scripts/validate_lab.py --env-file .env --url http://localhost:18082 --tc-url http://localhost:18111 --refresh --timeout 900
```

При аварийном завершении процесса, отключении Docker или ошибке cleanup автоматическое восстановление
не гарантируется. По сообщённым ID проверьте только свои временные билды и сравните Composite/Beta
с манифестом; не отменяйте общую очередь. Затем повторите `expand_lab.py --plan` перед продолжением.

## 7. Unit и браузерные тесты

```bash
pytest
docker compose -f compose.e2e.yaml up --build --abort-on-container-exit --exit-code-from browser-e2e
docker compose -f compose.e2e.yaml down --volumes --remove-orphans
```

Последняя команда удаляет только изолированный E2E-стенд и его временные volumes; не подставляйте
в неё `compose.yaml`. Обычный E2E проверяет demo в отдельной БД, не подключаясь к Cloud/TC.

Live-сценарии из [`e2e/test_lab_matrix.py`](../e2e/test_lab_matrix.py) включаются явно.
Установите Chromium и передайте через защищённое окружение `E2E_WEB_USERNAME`/`E2E_WEB_PASSWORD`
с реальными web-учётными данными; эти переменные не читаются автоматически из `.env`.
Пример для Linux после безопасного заполнения переменных:

```bash
python -m playwright install --with-deps chromium
E2E_LAB_MATRIX=1 E2E_BASE_URL=http://localhost:18082 pytest -c e2e/pytest.ini e2e/test_lab_matrix.py
```

В PowerShell задайте `$env:E2E_LAB_MATRIX='1'` и `$env:E2E_BASE_URL='http://localhost:18082'`,
затем выполните ту же команду `pytest`. Не вставляйте секрет в аргументы командной строки или Git.

Live-браузерные тесты читают граф: точность поиска в общем проекте, пять колонок и отсутствие
совпадающих позиций, скрытый 11-й репозиторий, Maven provenance и оба Python-тега в hover,
закрытие панели по клику мимо, безопасное экранирование/ограничение списка путей.
Они не заменяют сверку фактических билдов через `validate_lab.py`.

Архивация DC-проектов, корпоративные CA/VPN, производственные permissions и особенности
конкретного DC/TC здесь не эмулируются как якобы реальные: соответствующие контрактные тесты
